# Motion: build, render and routes
Part of the Motion Playbook (`motion-playbook.md` in the project root has the index, the working order, the ban list and the rubric). Sections 7, 13, 16, 17: build process, render capability and checks, Remotion route, Figma as a reference. Section numbers match the index.

## 7. Build process (do not rush, do not waste)
Run Section 0 first. This section is how the agreed piece is built and checked.
0. Reference first. Build the brief from a seen reference (the user's own reference beats any gallery) and write its measured values into the brief: transition durations, the cadence of small changes, overshoot, how much of the frame the hero fills, headline size.
1. Brief in numbers before any build (designer): one-line concept, beat-by-beat storyboard, shot list with frame ranges, camera move per shot, transition and carry-over per cut, tokens (easing, springs, durations, stagger), ban list, QA list. Replace adjectives with numbers.
2. Tokens file: all easing, spring, duration and stagger values live in one file. No inline numbers in scenes.
3. Rendered pieces: every frame is a pure function of time (`renderAt(t)`), no timers, no CSS transitions, no requestAnimationFrame, no clock, seeded randomness only, fonts loaded before frame 0, a freeze-frame parameter (`?t=`) so any frame can be viewed cheaply, loops that wrap with no doubled frame.
4. Pre-flight in code, before any render. Scan the source for the ban patterns (timers, CSS transitions, unseeded random, inline easing numbers, crossfades, linear spatial easing). Run a text-overlap test on sampled frames using bounding boxes. This catches basic mistakes for free. It also runs the Section 0a checks: read-time ratio, velocity jumps, the foreground plus background sum, repeats between neighbouring sections, and the flow map. Run `python3 tools/preflight.py --brief <brief> --tokens tokens.json --frames frames.json` (see `tools/README.md`). It reports each broken guideline as a warning with a reason. Also run a framing check: mark the elements that must stay composed (each word of a headline, the hero card, the focused line) with `data-keep`, and report any that sit visibly (opacity above 0.6, not blurred) outside a 5% safe margin or cut by the frame edge. Flags inside a deliberate move or macro are fine; flags on a resting frame are camera misalignment, which the user rejects. Mark words, not line boxes, or hidden words cause false flags. Rotated cards are skipped by the overlap test (`data-tilt`) and checked by eye.
5. Review stills, not video (smoothness and flow are judged from plots and scans, Section 0a, since stills cannot show them): one frame per beat or shot, plus a frame mid-transition for every transition. Score each against Section 9 and compare it side by side with the reference at matching moments (same section, same beat). Measure rhythm with a frame-difference scan (longest still hold, small changes per second). A self-score never goes to the user without this comparison. Fix the three worst, by frame number. Two to four rounds, then one full render.
6. Do not re-check what has not changed. Keep a `verified` list (what, at which version). Re-run a check only when its inputs changed.
7. Fix classes of mistakes once. When a basic mistake appears, add it to the pre-flight and to the ban list so it is caught automatically next time. Propose the rule to the user for CLAUDE.md.
8. Self-scores are opinions. Back them with measurements where possible: position-per-frame plots, onion skins for spacing, the overlap test, sharpness checks on full-size frames.
9. Not a first draft: the storyboard is approved, the sample shot is approved (Gate 2), and at least two scored still-review rounds are done before the full render.
10. Cost: Opus writes the brief and judges. Sonnet builds. The checker reviews contact sheets and mid-transition frames, not whole videos. The full render happens once.

## 13. Render capability and checks
- Before promising an MP4, check what this environment can really do (Playwright with Chromium, ffmpeg, GPU). If it cannot render here, say so plainly: give a live preview here and the render command for the user's machine. Never claim a render that did not happen.
- Before the full render: one frame per beat (and one per transition midpoint), a frame-by-frame look at the loop boundary, and for fly-throughs a 30 fps preview with an optical-flow check that forward motion and zoom stay smooth and never reverse.
- Motion blur: 3-4 subframes blended with ffmpeg tmix (up to 16 for 3D finals).
- Defaults when the user skips an input: screenshots captured from the real product, logo, colours and typeface taken from the user's site or repo, music proposed for approval (library, made in code, or a mix), tempo 120 BPM if there is no track.
- Match cuts: the first frame on the beat continues the shape and motion of the last frame before it, never a blank or a flash. Keep full-frame flashes to one or two structural moments (the drop, the end card). A whip is one pan with both shots on screen, A sliding out as B slides in.
- Rhythm: a small change in the focus every 0.3-0.6 s (a field fills, a row arrives, a number ticks), a new idea every 2-4 s, and no still hold over about 0.9 s (a still hold is one with no change in the focus). A moving push alone does not carry a hold longer than about 1 s. A line stays up past 0.9 s only while its focus keeps changing (Section 0a-A).
- Anything drawn after the motion-blur accumulation (grain, glitch) goes in a post step, or the subframe average erases it.
- Review at phone size too: a half-size sheet, as a phone at arm's length. Every word the viewer must read survives it.
- Any character outside basic Latin (arrows, check marks, superscripts, CJK) is checked against both faces' glyph tables first. A fallback glyph breaks the two-face rule.
- Every accent (hit, whoosh, stamp) is listed once in one table `[beat, label, sound]`. The sound is generated from that table, so picture and sound cannot drift.
- Render efficiency (from the video-making skill): aim for one full render per request. Draw a few frames at full size at the busiest moments and look at them first. Render one encoded file per scene (same size, fps and encoder settings), written to a temporary name ending in .mp4 and renamed when ffmpeg exits 0, then join with the concat demuxer and `-c copy`. Our handoffs overlap, so a scene file runs from one handoff midpoint to the next. Changing one scene means re-rendering its file and the neighbours that share its handoff. New sound or a shorter end: `-c:v copy` without re-encoding the picture. Web captures: JPEG at quality 92, not PNG. The confirmed spec sets the fps (the skill's 30 fps default does not override it). When Remotion renders the film, use its own render route and keep these habits.
- Render progress is always shown: every render script prints one line per half second of film with percent, frame n/N, elapsed and ETA (`tools/threejs-film/record.py` does; copy its `progress()`). For Remotion use its own progress output (`npx remotion render` prints percent and frames) and relay it. A long render runs in the background and the user is told the percent and ETA when it starts and at each check. Never render silently.
- Real elements only: before building, list every scene's elements and where each comes from (supplied asset, library icon, or built here). Logo, product shots and UI come only from the user's files or repo, used as given. Never redraw, approximate or invent a substitute for a brand mark. If an asset is missing, unusable or too low resolution, say so and ask, or use a clearly labelled placeholder. No stand-in shapes presented as the real thing.
- Backgrounds: start from `motion/backgrounds.md` as guidance (remix, recolour, blur, layer, re-animate or invent), apply its quality checklist and rotation rules.
- After the final render: probe the file (duration, fps, pixel format, audio present) and pull a frame from the encoded file, not the source.

## 16. Remotion route (when the film is built in Remotion)
Engine choice: Remotion or HyperFrames are both allowed, pick per project at the recommended-spec step with a one-line reason. Remotion: React, deterministic, best for UI and type heavy films and the default. HyperFrames: HTML and GSAP compositions; locally via `npx skills add heygen-com/hyperframes` (files stay on the machine); the hosted MCP (compose and render tools) is only for chat clients and sends assets and prompts to a third party, so say that before using it and check the tool description in the session. Its built-in house styles are not accepted as is: apply the colour-range, background and rotation rules. Three.js films use `tools/threejs-film/`.
Read the Remotion router skill first, then its markup guide. The referenced files (transitions, 3D, effects, sound effects, audio visualisation, text measuring, calculate-metadata, parameters, connected compositions) were listed but not read on 2026-11-23, so read the relevant one before using that feature.
- Drive everything from the frame number (`useCurrentFrame` and `interpolate`). No CSS transitions or animation classes. They do not render.
- Easing: `Easing.bezier` and `Easing.spring`. Use the `scale`, `translate` and `rotate` properties instead of one `transform` string. Animate scale with its perceptual-scale output, which matches the log-space dolly rule (Section 6b). Keep each `interpolate` inline in the `style` so Studio can edit it.
- Give layers names (`Interactive.*` and named scenes) and make each substantial scene a connected composition, so the user can retitle, retime or fix it in Studio without a round trip.
- Preserve user changes: if the code changed outside the conversation, do not overwrite it. Assume it was intentional or ask.
- Fonts: brand fonts through the local fonts route, self-hosted with the licence kept. The Google Fonts loader is fine for a rendered video only if the licence is checked and the font is in `CREDITS`.
- Parameters (a Zod schema) are the right way to make the format variants (16:9, 9:16, 1:1) from one composition.
- Check visually in Studio or by rendering single frames, as in Section 13.

## 17. Figma as a reference or source
- A Figma link in the brief is read through the Figma tool first (Reference Intake, step 2).
- If the frame is animated, read its real motion with `get_motion_context`: keyframes, easing curves and timeline. Write those measured values into the brief. Do not guess them from a screenshot.
- A Figma animation can be exported as an MP4 (`export_video`) to use as a reference or a base. Only top-level frames own a timeline. The result is the user's own work and counts as theirs to use.
- Writing back into the user's Figma file needs the Figma skills and a session. Do not edit their file without asking.
